# 投资体系大版本升级工作流 Skill

## 一、用途

当用户的投资体系（规则集/评级表/评分维度）需要大版本升级时，提供标准化的工作流，避免：
- 改一个规则牵连一片，导致自相矛盾
- 没等用户确认就动手改
- 改完不同步到所有引用处

**核心四步：** 逐项确认 → 分批替换 → 全量审计 → 三层同步

## 二、触发条件

任一命中即启动：
- 用户说"升级到 V5.X""新增规则""调整评级""修改分制"
- 用户说"你把 XXX 也同步了""所有引用都要改""列个清单看影响范围"
- **关键否定信号**：用户说"不要总乱改""别全动""先问再改" → 必须用此 skill

## 三、工作流

### Step 1：列影响清单（不动手）

收到升级指令后，**第一步是列清单**，不直接动手改。

输出格式：

```markdown
## 升级影响清单

### 核心规则改动（1-2 个）
1. [规则名] [当前版本] → [目标版本]
   - 影响章节：§X.X, §Y.Y, §Z.Z
   - 影响文档：SKILL.md / references/A.md / references/B.md
   - 影响代码：scripts/xxx.py

### 连带改动（N 个）
2. ...
3. ...

### 待用户确认项
- [ ] 改动 1 是否执行？
- [ ] 改动 2 是否执行？
- [ ] 连带改动 N 是否一起改？
```

**等用户逐项确认后再进入 Step 2。**

### Step 2：分批替换

用户确认后，**按依赖顺序分批改**，不一次性全改。

**顺序原则：**
1. 先改核心规则（1-2 个）
2. 再改连带引用（N 个）
3. 最后改跨文档引用（references/、外部文档）

**每批改完汇报一次**，等用户说"继续"再改下一批。

### Step 3：全量审计

全部改完后，**审计所有改动**：

```markdown
## 审计报告

### 改动统计
- 章节改动：X 处
- 文档改动：Y 个文件
- 代码改动：Z 个脚本

### 一致性检查
- [ ] 所有 §X.X 引用已更新
- [ ] 所有版本号已统一
- [ ] 所有评级表已同步
- [ ] 没有遗留的旧版本引用

### 矛盾检查
- [ ] 新规则与旧规则不冲突
- [ ] 评分维度加减后总分仍一致
- [ ] 分制调整后所有评分已重算
```

### Step 4：三层同步

改动必须同步到 3 层：

| 层级 | 内容 | 同步方式 |
|------|------|---------|
| L1 | 本地 skill 文件 | 直接写文件 |
| L2 | 用户的工作上下文（如 Get 笔记） | API 推送 |
| L3 | 触发该 skill 的所有 cron job | 更新 cron prompt |

**铁律：** 改了任何一层，必须检查另外 2 层是否需要同步。

## 四、多件事并行处理

用户可能一次说多件升级事项（如"加 X 规则 + 改 Y 评级 + 删 Z 维度"）。

**正确做法：**
- Step 1 一次列出所有 N 件事的影响清单
- Step 3 一次给齐所有改动（不逐项汇报）
- Step 4 一次同步完所有层级

**错误做法：**
- 改完 1 件汇报 1 次，等确认才改下一件 → 来回 N 轮
- N 件事来自同一份复盘，改完任意 1 件后其他必须配套改（否则体系自相矛盾）

## 五、严重违纪清单

以下行为直接踩坑：

| # | 违纪行为 | 后果 |
|---|---------|------|
| 1 | 没列清单就动手改 | 改错方向，全盘返工 |
| 2 | 改一个规则不查连带影响 | 引用处自相矛盾 |
| 3 | 改完不审计 | 遗留旧版本引用 |
| 4 | 改完不同步到 cron | 定时任务用旧规则 |
| 5 | 用户说"全改"就真的全改 | 改了不该改的 |
| 6 | 假设"已删除"的笔记真的不存在 | 实际可能只是 App 端视觉删除，云端还在 |
| 7 | L1 改了但 L2 没同步 | 用户在 App 看到旧版 |

## 六、常见陷阱

### 陷阱 1：L1 字符上限

L1（本地 skill 文件）可能有字符上限（如 3000 字符）。改动后超限 → 必须拆分或精简。

**应对：** 改动前先检查当前长度，预判是否会超限。

### 陷阱 2："已删"假设错误

用户说"某篇笔记已删"，不等于该笔记真的不存在：
- 可能是 App 端手动删除（云端还在）
- 可能是用户的另一种表达（"不要了"≠"删了"）

**应对：** 引用任何笔记 ID 前，先 GET 验证是否存在。

### 陷阱 3：recall 排序不稳定

笔记系统的语义搜索结果排序可能不稳定，同一 query 不同时刻返回不同顺序。

**应对：** 不能依赖"第一个结果就是目标"，必须按标题+内容双重确认。

### 陷阱 4：模型 fallback

delegate_task 指定模型 A，实际可能 fallback 到模型 B。

**应对：** 升级报告的"重要说明"段必须写实际跑的什么模型，不假装。

## 七、升级记录模板

每次升级完成后，写入升级记录：

```markdown
## V5.X → V5.Y 升级记录

**日期：** YYYY-MM-DD
**触发：** 用户要求 N 件事（列出）

### 改动清单
1. [规则名]：旧 → 新
2. ...

### 审计结果
- 章节改动：X 处
- 一致性检查：✅ 通过
- 矛盾检查：✅ 无矛盾

### 同步状态
- L1：✅ 已同步
- L2：✅ nid=XXX 已更新
- L3：✅ N 个 cron 已更新
```
