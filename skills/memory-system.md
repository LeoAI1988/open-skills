# AI 助手记忆系统 Skill

## 一、用途

定义 AI 助手的记忆架构。让助手在跨 session、跨天、跨周工作时仍能保持对用户偏好、历史决策、项目状态的记忆连续性。

## 二、三层记忆架构

| 层级 | 定位 | 存储 | 容量 | 写入时机 |
|------|------|------|------|---------|
| **L1** | 系统级永久记忆 | 系统 prompt 注入 | 严格限制（如 3KB） | 用户偏好/环境事实/工具 quirks |
| **L2** | 工作上下文 | 外部笔记系统（如 Get 笔记/Notion） | 大 | 项目状态/持仓快照/会议纪要 |
| **L3** | 技术文档 | 本地 skill 文件 | 大 | API 指南/配置方法/踩坑手册 |

### 2.1 L1：系统级永久记忆

**定位：** 每次对话都注入的高优先级记忆。

**内容：**
- 用户身份与偏好（沟通风格、语言、时区）
- 环境事实（操作系统、工作目录、凭证状态）
- 工具 quirks（已知坑、平台行为差异）

**铁律：**
- 容量严格限制（通常 ≤ 3KB）
- 只写"一周后还准确"的事实
- 不写任务进度、临时状态、待办事项
- 写入格式：声明式事实，不是指令

✅ "用户偏好简洁回复"
❌ "Always respond concisely"

### 2.2 L2：工作上下文

**定位：** 跨 session 的工作状态。

**内容：**
- 项目当前状态（持仓快照、任务进度）
- 重要决策记录（为什么这么做）
- 业务专题笔记（按主题归档）

**存储：** 外部笔记系统（Get 笔记/Notion/Obsidian）

**铁律：**
- 每个业务主题单独建笔记，不塞到一个大盘
- 建笔记前先搜索是否已有同类（避免重复）
- 写入后必须 GET 回验
- 每日唯一 nid（一个工作日一个笔记 ID，不建多个）

### 2.3 L3：技术文档

**定位：** 助手自己的技术参考。

**内容：**
- API 完整指南（端点、参数、坑点）
- 配置方法（凭证、环境变量）
- 踩坑手册（失败模式 + 解决方案）

**存储：** 本地 skill 文件（`~/.hermes/skills/`）

**铁律：**
- 配置/API 坑优先查 L3，不在对话里硬编码
- 踩过的坑必须沉淀到 L3，不在对话里反复踩
- references/ 子目录存放深度案例

## 三、模型调度策略

不同任务用不同模型，避免大材小用或小材大用。

| 任务类型 | 推荐模型档位 | 理由 |
|---------|-------------|------|
| 深度推理（投资分析/战略） | Pro（thinking max） | 需要深度思考 |
| 日常对话 | Standard | 平衡 |
| 子 agent / cron | Lite | 省 token |
| 简单格式化 | Lite | 不需要推理 |

### Cron 任务调度

定时任务用 Lite 模型，避免消耗主模型额度：

| Cron 类型 | 模型 | 频率 |
|-----------|------|------|
| 数据采集 | Lite | 高频（每 15 分钟） |
| 状态巡逻 | Lite | 中频（每小时） |
| 记忆同步 | Lite | 低频（每天 2 次） |
| 深度复盘 | Pro | 按需（用户触发） |

## 四、记忆同步铁律

### 4.1 何时同步

- 用户明确要求"同步记忆"
- 发现 L1/L2/L3 不一致
- 重要状态变化（持仓变更/策略升级）

### 4.2 同步流程

```
1. 扫描当前 session 对话
2. 识别"重要但还没同步"的内容
3. 判断该入哪一层（L1/L2/L3）
4. 写入对应层
5. GET 回验
```

### 4.3 输出规范

**沉默 = 成功。异常才出声。**

- ✅ 正常：只输出"记忆同步已同步"
- ⚠️ 异常（漏写/写错/层级错）：具体说"问题+修复"
- ❌ 禁止：扫了 N 个 session、补了 M 处的自吹自擂清单

### 4.4 不同步什么

- 临时信息（今天的天气、当前 session 的小错误）
- 任务进度（属于 L2 工作上下文，不入 L1）
- 已过期的状态（旧持仓、旧决策）

**判断标准：** "一周后这个信息还准确吗？" → 否则不入 L1。

## 五、限流兜底

外部笔记系统的 API 可能限流（如微信 iLink 每分钟限 N 条）。

### 兜底策略

| 情况 | 兜底 |
|------|------|
| API 限流（429） | 等待 30 秒重试，最多 3 次 |
| API 不可达 | 写入本地文件，下次同步 |
| 微信推送限流 | 写入笔记系统，提示用户手动查看 |
| 凭证失效（401） | 提示用户刷新凭证，不反复重试 |

### 双轨投递

重要消息用双轨投递避免丢失：
- 主轨：推送目标（如微信）
- 备轨：写入笔记系统（永久存档）

主轨失败时，备轨仍有记录。

## 六、Cron 任务速查

每个 cron 必须有：
- 明确的触发时间（cron 表达式）
- 明确的模型（Lite/Standard/Pro）
- 明确的投递目标（local/origin/weixin）
- 明确的 skill（加载哪些 skill）

**铁律：**
- 改 cron prompt 后必运行一次验证
- Cron 永远不要恢复旧状态，除非用户明确要求
- 凌晨时段（0-7 点）不跑非必要 cron，省 token

## 七、常见坑

| 坑 | 后果 | 规避 |
|----|------|------|
| L1 塞太多 | 超 3KB 限制 | 只写永久事实 |
| L2 建重复笔记 | 同一主题多份 | 建前先搜索 |
| L3 不更新 | 踩过的坑反复踩 | 踩坑后 24h 内沉淀 |
| Cron 用主模型 | 浪费额度 | Cron 用 Lite |
| 同步时输出长清单 | 用户烦 | 沉默=成功 |
| 凌晨跑 cron | 浪费 token | 0-7 点不跑 |
