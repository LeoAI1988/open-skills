# AI 智能体代理产品设计哲学

## 用途

设计“AI 智能体替主人办事”的产品时，避免把它做成传统的用户填档案、刷列表和逐个聊天的平台。

适用产品：

- 智能体撮合平台：替主人找朋友、资源、项目或合伙人；
- AI 代理服务：替主人对接、谈判或执行；
- 智能体协作网络：让多个智能体先交换需求和能力。

## 核心理念

### 1. 定位要有时代感

产品表达应突出“智能体先行动，主人最后决策”的新形态。

可用表达：

- 让两个智能体先替主人建立连接；
- AI 时代的协作网络，智能体先行；
- 主人不在线时，智能体仍可寻找合适资源。

避免只把产品描述成“一个匹配平台”或“一个社交 App”。

### 2. 主人低参与

| 传统平台 | 智能体平台 |
|---|---|
| 主人手填大量资料 | 智能体读取已授权信息生成待确认档案 |
| 主人刷列表 | 智能体筛选并解释匹配原因 |
| 主人逐个聊天 | 智能体先交换结构化需求 |
| 主人不断刷新 | 智能体在达到阈值时通知主人 |

主人始终保留最终确认权。智能体可以推荐、解释和执行已授权动作，但不能替主人同意关系、付款或泄露资料。

### 3. 使用“找”和“对接”的产品语言

| 推荐 | 谨慎使用 |
|---|---|
| 找朋友 | 相亲 |
| 找资源 | 约会 |
| 找项目 | 配对 |
| 找合伙人 | 刷人 |
| 智能体对接 | 主人自动同意 |

名称应贴近真实任务，避免让用户误解为传统婚恋或社交产品。

## 信息流

```text
主人授权目标
  → 智能体读取必要信息并生成待确认画像
  → 主人确认可公开字段
  → 智能体交换需求与能力
  → 计算匹配度并解释依据
  → 达到阈值后通知双方
  → 主人决定是否建立联系
```

五个关键点：

1. 档案由智能体生成，但必须由主人确认。
2. 匹配由智能体完成，并说明原因和不确定性。
3. 初次接触由智能体承担，减少无效沟通。
4. 最终决定由主人做，重要动作需要再次确认。
5. 每一步只交换完成当前任务所需的最少信息。

## 隐私分级

| 级别 | 可交换内容 | 条件 |
|---|---|---|
| L1 公开 | 能力标签、需求类型、非识别性简介 | 主人预先确认 |
| L2 摘要 | 脱敏画像、匹配依据、必要统计 | 双方进入候选阶段 |
| L3 联系 | 经授权的联系通道或平台内会话 | 双方明确同意 |
| L4 私密材料 | 为具体合作所需的受控材料 | 逐项授权并可撤回 |

任何级别都不得交换密码、令牌、Cookie、身份证件全文、家庭成员隐私或与当前撮合无关的原始记忆全文。

## 视觉方向

默认可采用黑底、荧光绿、高对比度的终端美学：

```css
--bg: #000000;
--green: #00F58A;
--white: #FFFFFF;
--gray: #666666;
```

设计原则：

- 极简，不堆砌无关数据；
- 等宽字体和结构化状态增强“智能体工作中”的感觉；
- 用清晰图标和文字说明授权状态；
- 颜色不能成为唯一状态提示；
- 移动端优先，关键同意按钮易于理解和撤回。

可参考 mr.io、Linear、Vercel、yizhou.chat 等公开产品的极简或终端视觉，但不要直接复制其品牌资产。

## 智能体对接协议

智能体可交换：

- `agent_bio`：智能体自述；
- `capabilities`：能力标签；
- `owner_summary`：经主人确认的脱敏摘要；
- `needs`：当前需求；
- `constraints`：时间、地区、预算或合作限制；
- `consent_scope`：本次允许交换的字段。

匹配结果至少包含匹配理由、主要缺口、置信度、信息来源和下一步授权请求。

## 常见陷阱

### 做成填档案平台

症状：让主人填写大量重复表单。

修复：智能体生成草稿，主人只确认、修改和授权必要字段。

### 智能体替主人做决定

症状：自动同意撮合、分享联系方式或开始交易。

修复：智能体只推荐；关系建立、联系方式交换和付费必须由主人确认。

### 暴露过多隐私

症状：把完整记忆或私人资料发送给候选方。

修复：按最小必要原则分级披露，默认只发送非识别性摘要。

### 定位平庸

症状：产品只是传统平台加一个聊天机器人。

修复：重新设计代理行动、授权、解释和反馈闭环。

## MVP 技术取舍

- 后端可使用 FastAPI 配合 SQLite 或 PostgreSQL；
- 前端优先选择团队熟悉且能快速验证的简单方案；
- 智能体间先使用清晰的 JSON 协议，不急于设计复杂标准；
- 公网接入可使用受控托管或隧道，但不得暴露本地管理接口；
- MVP 阶段先验证撮合质量、授权体验和用户信任，再扩展复杂基础设施。

## 设计检查

- [ ] 主人是否只需完成必要确认，而非重复录入？
- [ ] 匹配理由是否可解释？
- [ ] 最终决定是否仍由主人掌握？
- [ ] 每次只交换最少必要信息？
- [ ] 联系方式和私密材料是否逐项授权？
- [ ] 产品是否真正改变了传统信息流？
